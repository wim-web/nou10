# nou10 の文書作成

このリポジトリ専用の文書作成・整理ルール。文書を残すことを前提にせず、情報そのものが必要かを判断する。

## 内容の判断

- 書く前に、対象の実装・型・コメント・テストと CLI のヘルプを確認する。設定例は `examples/`、検証・リリースの定義は `.github/workflows/` と `scripts/` を参照する。
- コマンドの引数・既定値、設定や AppSpec の項目、payload・台帳の構造、状態遷移、フックの実行順序、検証項目を日本語で再記述しない。コードやヘルプを見れば分かる説明は、変更への追随漏れで矛盾する。
- 残すのは、目的、設計を選んだ理由、避けた代案とその問題、判断に影響する制約、運用者が維持する前提、外部サービスの制約、未決事項。理由という見出しでも、本文が動作説明だけなら削る。理由を後付けしない。
- README は目的・最小の導入手順・参照先に絞る。ホスト設定、AppSpec、systemd、Actions の使い方は既存のサンプルへ案内し、コードを転記しない。
- 完了した計画・作業ログ・検証結果・AI 利用の経緯は載せない。必要なら git の履歴から読む。開発途中の仮称や版を基に、存在を確認していない旧版利用者向けの互換性・移行案内を作らない。
- GitHub の権限やイベント発火条件など、コードだけで確かめられない外部の事実を残す場合は、公式情報を確認して根拠をリンクする。

## 文書の配置

- 設計理由と運用上の前提は `docs/design.md`、エージェントの作業ルールは `AGENTS.md` に置く。新しい文書には、既存文書やコードへの参照では足りない理由が必要。リンクを中継するだけの一覧は作らない。
- `.agents/skills/` のスキルは作業手順の定義であり、文書整理の名目で削る対象にしない。
- ファイル数を減らすために単純結合しない。重複と不要な情報を削り、必要な部分だけを読める構成にする。
- 削除対象を別の文書やコメントへ丸ごと移さない。コード側に補足する場合も、実装から自明でない契約・理由だけを該当箇所へ短く書く。

## 精査と確認

- 精査では各文書の本文を1文ずつ実装・ヘルプ・サンプルと照合する。見出しやキーワード検索だけで必要と判断しない。
- 精査・一覧だけを求められた場合は編集せず、ファイルごとに残す・縮小する・削除するの判断と、残す内容・削る内容・根拠を示す。
- 作成・修正後は、リンク先・アンカー・削除済み文書への参照を確認する。コードで分かる説明や、根拠のない設計理由が増えていないか読み直す。

# v0.1 実装メモ

2026-10-03の仕様案を基に実装しています。

## 状態と実行順序

```text
初回の完全な一覧取得 → baseline保存 → 新規要求を作成順に受理
queued → downloading → starting → running → done
                           └─────────┴─ クラッシュ/中断 → unknown + target hold
```

要求の状態と結果送信待ちリストは、同じbboltトランザクションに保存します。
bboltのfsyncを有効にした通常モードを利用し、CGOへの依存を避けています。
DBが壊れている・別ターゲットのDBである・保存に失敗する場合は処理を続けません。

1. 全ページを取得してから、対象の要求を一括受理する。
2. `queued` の報告を送る。
3. Release配下のasset一覧で所属を確認し、APIのasset IDから取得する。
4. サイズ・SHA-256・アーカイブ・manifest・AppSpecを確認してファイルを同期する。
5. 実行開始の意図（`starting`）と `in_progress` の送信待ちを保存する。
6. `in_progress` の送信成功後、開始期限を再確認して `running` を保存し、内蔵の配備処理を開始する。
7. 終了結果とその送信待ちを保存してから、GitHubへ報告する。

開始報告が失敗した場合、同一プロセス内では `starting` から報告を再試行できます。
その間に再起動した場合は、実際に子プロセスを起動していなくても保留します。
開始意図と外部プロセス起動を原子的にできないため、安全側の判断として採用しています。

結果報告はat-least-onceです。APIで受理された直後、送信済みの保存前にクラッシュすると、
同じstatusが再投稿されることがあります。フックは再実行しません。
重複要求のDeployment IDには、合流時の状態と以降の状態を報告します。
全statusで `auto_inactive: false` を指定し、同じenvironmentの別アプリや過去要求の状態に影響させません。

## ポーリング

repository・environment・taskで絞り込み、payloadのapplicationで振り分けます。
applicationのないpayloadや別アプリのpayloadは、このホストの所有物と判定できないため無視します。
対象アプリの未知schema・不正フィールド・期限切れは `error` にします。

基準位置は初回の最大Deployment IDです。各ポーリングで全ページを読み、処理済みIDを台帳と照合します。
ページごとにETag・応答本体・nextの有無をキャッシュします。途中のページが失敗した場合、
要求は一切取り込まず、永続基準位置を進めません。ページ移動で一時的に見落としたIDは次の完全走査で再取得します。
キャッシュはメモリ上にのみ保存します。

開始済みの実行中は新規要求をポーリングせず、完了後に取得します。
30秒の既定間隔、`X-Poll-Interval`、指数バックオフ、`Retry-After`、レート制限reset時刻を利用します。
結果POSTは少なくとも1秒間隔にします。401/通常403は15分待機します。
結果送信が未完了の間は次の実行を始めません。

## アーカイブの制限

既定値はダウンロード512 MiB、展開データ2 GiB、100,000エントリです。
展開上限にはtarヘッダーやpaddingも含みます。manifest/AppSpecは各1 MiBまでです。
ディスクへ展開せずに全エントリを検査し、gzipの末尾チェックサムまで確認します。
絶対パス、`..`、危険なパス表記、重複、ファイルを親にするパス、リンク、特殊ファイル、
setuid/setgid、拡張属性、sparse、隠された後続アーカイブを拒否します。
v0.1では安全なリンクも含めてリンク全般を非対応としています。

AppSpecは `version: 0.0`、`os: linux` に限定します。YAML aliasと複数ドキュメントを拒否し、
各フックが配布物中の実行可能な通常ファイルを参照していることを確認します。
解析・展開・ファイル配置はGoコード内で行い、フックスクリプトだけを子プロセスとして実行します。
未対応の設定は厳格なYAML解析で拒否します。対応範囲は [AppSpec対応範囲](appspec.md) を参照してください。

## Goによるローカル配備

`internal/appspec` が設定を厳格に解析し、`internal/bundle` が検証済みtgzを新しい専用ディレクトリに展開します。
`internal/host` が前回成功した版の停止フック、今回の配置、権限設定、起動と正常性確認を実行します。
外部CodeDeployバイナリ・AWS SDK・CGO・tarコマンドへの依存はありません。フックに必要なシェルやアプリ固有のコマンドはホストに用意します。

ファイル操作はGoの `os.Root` で `install_root` 内に制限します。既存のシンボリックリンクを拒否し、
新しいファイルは同じディレクトリ内の一時ファイルを同期してからrenameします。配備全体を原子的に置換する方式ではありません。
前回成功時に自分で配置したファイルだけを追跡し、次の配備で不要になったファイルを削除します。
空ディレクトリや外部から持ち込まれたファイルを再帰削除しません。

成功したジョブに `installation.json` を同期保存してから、agentが台帳の成功状態と前回成功参照を更新します。
フック失敗ではこの参照を更新しません。配置途中や失敗後の変更は自動復元しません。
配置履歴の保存に失敗した場合も、結果不明として保留します。

フックの通常の非0終了はfailure、検証・ファイル操作の失敗はerrorです。
全体の実行上限、各フックの上限、キャンセル、シグナル終了は結果不明として保留します。
停止時はフックのプロセスグループへSIGKILLを試みます。別セッションに離脱した処理の停止は保証できないため、
保留解除には運用者の確認が必要です。アプリのデーモンはsystemdなどに管理させてください。

## 検証範囲

自動テスト:

| 受入条件 | 検証内容 |
| --- | --- |
| 要求取得から実行・報告 | 模擬GitHub API → agent → 実行インターフェース、開始前と終了後の永続化順序 |
| 成否とGHA待機 | successのみ成功、failure/error/inactive/観測不能で失敗 |
| 不正要求の拒否 | 別ターゲット、未知schema、可変ref、期限、asset所属、ハッシュ |
| 重複と通常再起動 | 同一要求の合流、内容衝突の拒否、終了済み要求を再実行しない |
| 報告時の通信断 | 終了を保存したまま報告だけを再送 |
| クラッシュ | starting/runningをunknownに変更、後続要求を保留 |
| 過去assetへの再配備 | 別request IDなら同じassetを実行 |
| 認証と制限 | 401、通常403、primary/secondary rate limit、429、503 |
| 排他 | 同じtargetの二重ロック取得を拒否。task変更でも同じロック |
| 初期化 | 初回取得履歴を実行しない。失敗したページ走査を受理しない |
| 配布物と資格情報 | 不正tgz、サイズ制限、manifest、PATのredirect転送防止、フック環境 |
| ローカル実行 | Ubuntu 24.04の非rootユーザーで、外部CodeDeployなしに初回・更新・フック・権限・競合ポリシー・タイムアウトを実行 |
| 全体結合 | 模擬GitHub API → Goによる実配備 → 結果送信失敗/再送 → 前回成功履歴の引き継ぎ |

本番GitHubリポジトリへの要求作成・PAT権限・GitHub-hosted Actions・実際のアプリ/systemdを通す受入試験は未実施です。
コードとサンプルを配置しただけでは本番受入完了とは扱いません。

残る実環境の確認手順:

1. ホストでdoctorと初期化完了を確認する。
2. 保護されたdefault branchからサンプルを調整したworkflowを実行し、アプリの更新とsuccessを確認する。
3. ValidateServiceを失敗させ、GHAも失敗することを確認する。
4. 結果POST時の通信断で、フックを繰り返さず報告だけが復旧することを確認する。
5. 実行中のプロセス停止で保留されることを確認し、手順に従ってrecoverする。

## 対象外

複数ホストへの同時展開・ローリング更新・LB連携・自動ロールバック・DB復元・リモートキャンセル・
GitHub App認証・GUI・ログ転送・自己更新・汎用ビルド機能・台帳の自動圧縮/削除は実装していません。
